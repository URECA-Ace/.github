본 시스템은 **대규모 트래픽 환경에서 선착순 쿠폰 발급 시 발생하는 동시성 문제와 데이터 정합성을 안정적으로 처리하는 것**을 목표로 합니다.

사용자의 쿠폰 발급 요청은 **Nginx**를 통해 전달되며, **Redis에서 재고 차감과 중복 발급 여부를 원자적으로 검증**합니다. 여기까지는 1차 구현으로 확정된 부분입니다.

발급에 성공한 요청을 **어떻게 영속화할 것인가**가 남은 설계 지점입니다. MySQL에 동기로 저장하는 방식과, **Kafka 이벤트 스트림을 거쳐 Consumer가 비동기로 저장**하는 방식을 놓고 비교 측정을 진행하고 있습니다. 정오 1초에 집중되는 1만 건이 커넥션 풀을 고갈시키는지, 비동기 전환이 실제로 얼마나 개선하는지를 수치로 확인한 뒤 결정합니다.

또한 **Prometheus + Grafana**로 TPS, 응답 시간, Redis/Kafka 상태를 모니터링하고, 별도의 정합성 검증 Runner를 통해 Redis와 MySQL의 데이터가 일치하는지 검증합니다.

## 🔧 기술 선택 이유

| 기술 | 선택 이유 |
|---|---|
| **Redis** | 대규모 동시 요청에서 DB에 직접 접근하지 않고 재고 차감과 중복 발급 검증을 빠르게 처리하기 위해 사용 |
| **Kafka** | 쿠폰 발급 처리와 DB 저장을 분리하여 대량의 이벤트를 안정적으로 처리하고 비동기 구조를 구성하기 위해 검토 |
| **MySQL** | 쿠폰 발급 이력과 사용자 데이터를 영구적으로 저장하고, Unique 제약 등을 통해 최종적인 데이터 정합성을 보장 |
| **Nginx** | 대량의 요청을 안정적으로 받아 백엔드로 전달하고 트래픽을 분산 |
| **JMeter / k6** | 대규모 동시 요청을 재현하여 쿠폰 발급 시스템의 성능과 동시성 제어를 검증 |
| **Prometheus + Grafana** | TPS, 응답 시간, Redis/Kafka 상태 등을 모니터링하여 병목 구간과 시스템 상태를 확인 |
| **Docker Compose** | Redis, Kafka, MySQL, 모니터링 환경 등을 동일한 환경에서 구성하고 쉽게 재현하기 위해 사용 |

> 각 기술의 **도입 근거는 비교 측정으로 검증**하고 있습니다. 아래 '단계적인 개선 방식' 참고.

## 🚀 단계적인 개선 방식

처음부터 Redis, Kafka 등 모든 기술을 적용하는 것이 아니라, **단계적으로 구현하고 부하 테스트를 수행하면서 시스템을 개선**하는 방식으로 진행합니다.

### 1️⃣ Redis 기반 초기 구현

먼저 **Redis만 사용하여 선착순 쿠폰 발급 기능을 구현**합니다.

- Redis Lua Script를 이용한 원자적 재고 차감
- 중복 발급 방지
- 재고 부족 여부 검증
- 발급 가능 시간 검증

이후 **대규모 동시 요청을 발생**시켜 Redis 기반 동시성 제어가 정상적으로 동작하는지 확인합니다.

### 2️⃣ 부하 테스트 및 문제점 분석

Redis 기반 구현의 테스트 결과를 바탕으로 다음 항목을 확인합니다.

- TPS
- 평균 및 최대 응답 시간 (p95 / p99)
- 동시 요청 처리량
- 재고 초과 발급 여부
- 중복 발급 여부
- DB 부하 (커넥션 풀 대기)
- Redis 처리 한계 및 병목 구간

#### 기술 선택 근거를 위한 비교 측정

"Redis를 왜 쓰는가", "저장을 왜 비동기로 돌리는가" 에 **말이 아닌 수치로 답하기 위해**, 별도 레포에서 발급 방식 4종을 **같은 조건으로 나란히 측정**하고 있습니다.
(https://github.com/URECA-Ace/Ace_LT)

| 비교 축 | 답하려는 질문 |
|---|---|
| MySQL 비관적 락 ↔ **Redis Lua 판정** | Redis를 왜 도입하는가 |
| 동기 저장 ↔ **비동기 저장** | 저장을 왜 분리하는가 |
| 인메모리 큐 ↔ **내구 로그(Outbox)** | 비동기면 충분한데, 왜 메시지 큐인가 |

재고, 데이터, 인스턴스 사양과 커넥션 풀 크기를 **고정한 채 동시 요청 수만 늘려가며** 각 방식이 어디까지 버티고 어떻게 무너지는지를 확인합니다.

특히 마지막 축은 **"비동기로 처리하면 되는데 굳이 Kafka를 왜 쓰는가"** 에 대한 테스트를 위한 것입니다. 프로세스를 강제 종료했을 때 인메모리 큐에서는 유실이 발생하고 내구 로그에서는 복구되는지를 직접 측정할 계획입니다.

### 3️⃣ Kafka 도입 검토

측정 결과 **DB 저장 부하와 동기 처리로 인한 지연이 실제 병목으로 확인되면** Kafka 기반 비동기 파이프라인을 도입합니다.

판단 기준으로 삼을 지표는 다음과 같습니다.

- 응답 p99가 저장 방식에 따라 유의미하게 갈리는가
- 커넥션 풀 대기(`hikaricp_connections_pending`)가 병목의 직접 증거로 나타나는가
- 장애 상황에서 **유실 건수** 차이가 발생하는가

```text
Client
  ↓
Nginx
  ↓
쿠폰 발급 API
  ↓
Redis (원자적 판정)
  ↓
발급 성공
  ↓
Kafka
  ↓
Consumer
  ↓
MySQL
```

### 1. 요구사항 / 정책 해석

- [ ] "재고 10,000장, 1인 최대 1매" 조건과 "발급 이력 300만 건" 더미데이터가 어떻게 양립하나요? 단일 캠페인 기준이면 최대 10,000건만 나올 수 있는데, 300만 건이 되려면 캠페인(쿠폰)이 여러 개 있어야 한다는 뜻인지, 그리고 취소·만료 등 상태변경 이력까지 합쳐서 300만인지 궁금합니다. (조성원)

- [ ] 쿠폰 만료/취소 후 재발급이 가능한지(취소된 쿠폰은 재고로 다시 돌아가는지) 궁금합니다. (조성원)

### 2. 정합성 검증

- [ ] 정합성 검증 부분을 진행할때, sql쿼리로 DB조회를 하여 비교검증하고 결과를 DB에 저장하는 식으로 구현하고 있는데, 정합성 검증을 이정도로 끝내도 되는건가?라는 생각이 든다. 아직 Redis, Kafka와의 동시 비교하는 로직은 작성하지 않았고, 검증결과에 실패했을때 처리 방법에 대한 방법도 생각을 못했는데, 혹시 정합성 검증 관련해서 이정도만 해도 되는지 궁금하다. (임진우)

- [ ] 정합성 검증 부분에, 검증 결과 리포트 자동화란 말이 있는데, 이것이 검사 결과를 DB에 저장해서 시각적으로 볼 수 있게 만들라는 것인지, 아니면 다른 의미인지 궁금합니다. (임진우)

- [ ] 재고 정합성 오차를 0으로 만드는 게 핵심 목표인데, 이걸 보장하는 데 있어 가장 중요하게 봐야 할 지점이 어디라고 생각하시나요? (Lua 원자성, DB Unique 제약, 이벤트 유실 방지 등) (조성원)

- [ ] 검증 결과 리포트를 구현할 경우, 리포트 안에 어떤 정보가 담겨있어야 하나요? (조성원)

### 3. 아키텍처와 기술 선택

- [ ] Lua Script 안에서 재고 검증·중복 발급 검증·오픈시각 검증·재고 차감·Stream XADD까지 한 번에 처리하는데, 이 로직이 너무 복잡한가요? 복잡하다면 어떤 다른 방향으로 풀어갈 수 있을지 궁금합니다. (조성원)

- [ ] Redis Stream을 Outbox로만 쓰고 Kafka 없이 Consumer가 직접 소비하는 구조와, 지금처럼 Kafka로 한 번 더 relay하는 구조 중 어느 쪽이 동시성 제어와 정합성에 더 효율적인가요? Relay Worker가 죽거나 지연되는 상황이 새로운 장애 포인트를 만들지는 않을까 걱정됩니다. (조성원)

- [ ] 메시지 큐나 이벤트 로그의 도입 근거를 데이터로 만들 때, 실무에서는 실제로 어떤 실험을 하시나요? 저희는 프로세스를 강제 종료시키고 "성공 응답 수 - DB 저장 건수"로 유실을 재려고 하는데, 이런 인위적인 kill이 실제 장애를 대표할 수 있는지 궁금합니다. 사후 정합성 배치로 대조하는 방식이 더 적절한가요? 그리고 Kafka를 쓰신다면 `acks`나 `min.insync.replicas`를 실제로 어떻게 잡고 계신가요? (구지민)

### 4. 부하 테스트와 측정

- [ ] 선착순 이벤트처럼 정해진 인원이 한 순간에 몰리는 부하를 잴 때, VU 고정(closed model) 과 도착률 고정(open model) 중 어느 쪽으로 하시나요? 둘 다 돌리시는지, 목적에 따라 하나만 쓰시는지 궁금합니다. 저희는 20,000명이 1건씩 동시에 쏘는 방식으로 잡았는데, 이 경우 서버가 느려지면 TPS도 같이 떨어져서 "초당 몇 건까지 처리 가능"을 말하기가 어려운 것 같습니다. "우리 시스템 최대 처리량"을 보고할 때는 어느 수치를 쓰시나요? (구지민)

- [ ] 비교 실험에서 병목을 드러내려고 커넥션 풀 크기를 일부러 작게(10) 고정했습니다. 그런데 "튜닝을 안 해놓고 병목이라고 부르는 것 아니냐"는 반박이 가능할 것 같습니다. 이런 통제값이 정당하려면 무엇을 같이 보여줘야 할까요? 그리고 실무에서 풀 사이즈는 무슨 기준으로 잡으시나요 - 코어 수, DB `max_connections`, 아니면 측정해서 정하시는지 궁금합니다. (구지민)

- [ ] 재고 10,000장에 20,000명이 요청하면 절반이 409(재고 소진) 로 응답됩니다. 이건 시스템이 정상 동작한 결과인데 부하 테스트 도구는 실패로 집계합니다. 에러율을 보고할 때 이런 "의도된 거절"을 빼고 계산하시는지, 실무에서는 정상 거절과 장애를 어떤 기준으로 나누시는지 궁금합니다. (구지민)

### 5. 구현 기준

- [ ] 과제 요구사항에 "로그에서 개인정보 마스킹"이 있는데, MySQL은 UNIQUE 제약 위반 시 `Duplicate entry 'tester@test.com' for key ...` 처럼 위반된 값을 에러 메시지에 그대로 넣습니다. 스택트레이스를 통째로 남기면 개인정보가 로그에 들어가고, 안 남기면 500 원인을 추적할 수 없습니다. 저희는 예외 메시지를 제외하고 스택 프레임만 기록한 뒤 `incidentId`로 응답과 로그를 잇는 방식으로 처리했는데, 실무에서는 원인 추적과 마스킹의 상충을 어떻게 푸시는지 궁금합니다. (구지민)
