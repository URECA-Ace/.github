## 💡 프로젝트 흐름

```text
캠페인 오픈 (매일 정오 12:00:00 / 회차당 10,000장)
    ↓
선착순 발급 요청 (정오 1초에 집중)
    ↓
Redis 원자 연산으로 재고 선점 / 중복 차단
    ↓
발급 이력 비동기 영속화 (내구 로그 경유 / 측정으로 확정)
    ↓
쿠폰 생애주기 관리 (발급 → 사용 / 취소 / 만료)
    ↓
정합성 검증 배치 (300만 건 전수 검증)
```

### 1차 / 2차 MVP 아키텍처

```
[1차 - 베이스라인]
Nginx → API×2 → Redis Lua(원자 판정) → MySQL 동기 저장


[2차 - 개선]
Redis Lua(판정 + XADD) → 202 즉시 응답
                       → Stream Relay → Kafka → MySQL 배치 저장
```

본 시스템은 **대규모 트래픽 환경에서 선착순 쿠폰 발급 시 발생하는 동시성 문제와 데이터 정합성을 안정적으로 처리하는 것**을 목표로 합니다.

사용자의 쿠폰 발급 요청은 **Nginx**를 통해 전달되며, **Redis에서 재고 차감과 중복 발급 여부를 원자적으로 검증**합니다.

발급에 성공한 요청을 **어떻게 영속화할 것인가**가 남은 설계 지점이었고, 이를 비교 측정으로 결정했습니다. MySQL 동기 저장은 동시 20,000 요청에서 **커넥션 풀 대기가 톰캣 스레드 200개 중 190개까지 차오르며** 응답 p99가 4.5초까지 늘어났습니다. 저장을 요청 경로에서 떼어내면 그 대기가 **0**이 되고 p99가 4배 이상 줄어듭니다. 커넥션 풀을 5배 늘려보는 것으로는 해결되지 않았습니다. 그래서 **비동기 저장 + 내구 로그(Outbox)** 구조로 확정했습니다.

또한 **Prometheus + Grafana**로 TPS, 응답 시간, Redis/Kafka 상태를 모니터링하고, 별도의 정합성 검증 Runner를 통해 Redis와 MySQL의 데이터가 일치하는지 검증합니다.

## 🔧 기술 선택 이유

| 기술 | 선택 이유 |
|---|---|
| **Redis** | 대규모 동시 요청에서 DB에 직접 접근하지 않고 재고 차감과 중복 발급 검증을 빠르게 처리하기 위해 사용. MySQL 비관적 락과 비교 측정한 결과 **락 방식은 동시 20,000에서 절반 이상이 응답을 받지 못했고 Redis 방식은 0%** |
| **Kafka** | 발급 처리와 DB 저장을 분리하는 것 자체는 Redis Stream으로도 되고, 브로커 장애 시 유실 0도 **Redis AOF만으로 확보**됨을 측정으로 확인. Kafka를 쓰는 이유는 **다중 컨슈머 그룹 팬아웃(persist / notify / metrics), 장기 리텐션 기반 재처리, 노드 복제**이며 이는 측정이 아니라 요구사항 판단 |
| **MySQL** | 쿠폰 발급 이력과 사용자 데이터를 영구적으로 저장하고, Unique 제약 등을 통해 최종적인 데이터 정합성을 보장 |
| **Nginx** | 대량의 요청을 안정적으로 받아 백엔드로 전달하고 트래픽을 분산. 앱 인스턴스를 2대로 나누면 **응답 p99가 45% 개선**되는 것을 확인 (단, 커넥션만 늘리는 것은 오히려 악화) |
| **k6** | 동시 20,000 재현에 JMeter는 부적합. JMeter 스레드는 **OS 스레드(스택 1MB)라 20,000개면 스택만 20GB**가 필요. k6는 goroutine 기반이라 4 vCPU 한 대로 20,000 VU를 생성. 실측 상한은 40,000~50,000 사이 |
| **Prometheus + Grafana** | TPS, 응답 시간, Redis/Kafka 상태 등을 모니터링하여 병목 구간과 시스템 상태를 확인 |
| **Docker Compose** | Redis, Kafka, MySQL, 모니터링 환경 등을 동일한 환경에서 구성하고 쉽게 재현하기 위해 사용 |

> 각 기술의 **도입 근거는 비교 측정으로 검증**했습니다. 아래 '단계적인 개선 방식' 참고.

## 🚀 단계적인 개선 방식

처음부터 Redis, Kafka 등 모든 기술을 적용하는 것이 아니라, **단계적으로 구현하고 부하 테스트를 수행하면서 시스템을 개선**하는 방식으로 진행합니다.

### 1️⃣ Redis 기반 초기 구현

먼저 **Redis만 사용하여 선착순 쿠폰 발급 기능을 구현**합니다.

- Redis Lua Script를 이용한 원자적 재고 차감
- 중복 발급 방지
- 재고 부족 여부 검증
- 발급 가능 시간 검증

이후 **대규모 동시 요청을 발생**시켜 Redis 기반 동시성 제어가 정상적으로 동작하는지 확인합니다.

### 2️⃣ 부하 테스트 및 문제점 분석

Redis 기반 구현의 테스트 결과를 바탕으로 다음 항목을 확인합니다.

- TPS
- 평균 및 최대 응답 시간 (p95 / p99)
- 동시 요청 처리량
- 재고 초과 발급 여부
- 중복 발급 여부
- DB 부하 (커넥션 풀 대기)
- Redis 처리 한계 및 병목 구간

#### 기술 선택 근거를 위한 비교 측정

"Redis를 왜 쓰는가", "저장을 왜 비동기로 돌리는가" 에 **말이 아닌 수치로 답하기 위해**, 별도 레포에서 발급 방식 4종을 **같은 조건으로 나란히 측정**했습니다.
(https://github.com/URECA-Ace/Ace_LT)

| 비교 축 | 답하려는 질문 |
|---|---|
| MySQL 비관적 락 ↔ **Redis Lua 판정** | Redis를 왜 도입하는가 |
| 동기 저장 ↔ **비동기 저장** | 저장을 왜 분리하는가 |
| 인메모리 큐 ↔ **내구 로그(Outbox)** | 비동기면 충분한데, 왜 메시지 큐인가 |

재고, 인스턴스 사양과 커넥션 풀 크기를 **고정한 채 동시 요청 수만 늘려가며** 각 방식이 어디까지 버티고 어떻게 무너지는지를 확인했습니다. 로컬(단일 머신)과 AWS(인스턴스 4대 분리) 두 환경에서 각각 측정해, 결론이 특정 환경 때문에 나온 것이 아님을 확인했습니다.

#### 측정 결과

목표 시나리오(재고 10,000 / 동시 20,000)에서의 응답 p99입니다.

| MySQL 락 | + Redis 판정 | + 비동기 저장 | + 내구 로그 |
|---|---|---|---|
| 14,203ms (에러율 50%) | 4,506ms | **1,101ms** | **846ms** |

| 계층 | 결론 | 근거가 된 수치 |
|---|---|---|
| **판정** | Redis 필수 | MySQL 락은 20,000에서 **에러율 50~84%**, 거절(409) 응답조차 돌아오지 않음. Redis는 0% |
| **저장** | 비동기 필요 | 커넥션 풀 대기 **190 → 0**, p99 **4.1배** 개선. **pool을 5배 늘려도 비동기의 3배 뒤** |
| **큐** | 내구 로그 필요 | 프로세스 강제 종료 시 인메모리 큐는 **전량 유실**, Stream은 **유실 0**. 성능 대가도 없었음 |
| **영속화** | **Redis AOF를 켜야 함** | 끄면 브로커 장애 시 **전량 유실**. "유실 0"은 AOF가 켜져 있을 때만 성립 |
| **인스턴스** | 앱 2대 이상 유효 | CPU가 분리되면 **45% 개선**. 단 **커넥션만 늘리면 악화**(에러 6% → 24%) |
| **사양** | 앱 4 vCPU 이상 | 2 vCPU에서는 CPU가 먼저 병목이 되어 아키텍처 차이가 드러나지 않음 |

**전 구간에서 초과 발급 0건**이며, 1인 1매도 별도 검증(1,000 요청 / 100 유저 → 발급 100건)했습니다.

> 위 측정은 발급 이력 테이블을 비운 상태에서 수행했으므로 **인덱스가 최적인 조건**입니다.
> 본 시스템은 이미 300만 건이 적재되어 있어 동기 저장이 측정값보다 **더 불리**하게 동작합니다.
> 즉 위 격차는 보수적으로 잡은 값입니다.

특히 마지막 축은 **"비동기로 처리하면 되는데 굳이 Kafka를 왜 쓰는가"** 에 답하기 위한 것이었습니다. 프로세스를 강제 종료했을 때 인메모리 큐는 대기 중이던 건을 전부 잃고, 내구 로그는 재기동 후 전량 복구했습니다. 소비자만 정지시킨 경우에도 재개 시 **171ms에 수렴**했습니다.

### 3️⃣ Kafka 도입 검토

측정 결과 **DB 동기 저장이 실제 병목으로 확인**되었으므로 비동기 파이프라인을 도입합니다.

판단 기준으로 삼았던 지표와 결과는 다음과 같습니다.

- 응답 p99가 저장 방식에 따라 유의미하게 갈리는가 → **4,506ms vs 1,101ms (4.1배)**
- 커넥션 풀 대기(`hikaricp_connections_pending`)가 병목의 직접 증거로 나타나는가 → **동기 190 / 비동기 0**
- 장애 상황에서 **유실 건수** 차이가 발생하는가 → **인메모리 큐 전량 유실 / 내구 로그 0**

다만 **내구성만 놓고 보면 Redis Stream + AOF로도 유실 0이 확보**됩니다. Kafka는 팬아웃/리텐션/복제가 필요한 시점에 도입하며, 그 판단은 측정이 아니라 요구사항 기준으로 합니다.

```text
Client
  ↓
Nginx
  ↓
쿠폰 발급 API
  ↓
Redis (원자적 판정 + XADD)
  ↓
발급 성공
  ↓
Kafka
  ↓
Consumer
  ↓
MySQL
```

### 2. 정합성 검증

- [ ] 정합성 검증 부분을 진행할때, sql쿼리로 DB조회를 하여 비교검증하고 결과를 DB에 저장하는 식으로 구현하고 있는데, 정합성 검증을 이정도로 끝내도 되는건가?라는 생각이 든다. 아직 Redis, Kafka와의 동시 비교하는 로직은 작성하지 않았고, 검증결과에 실패했을때 처리 방법에 대한 방법도 생각을 못했는데, 혹시 정합성 검증 관련해서 이정도만 해도 되는지 궁금하다.

- [ ] 정합성 검증 부분에, 검증 결과 리포트 자동화란 말이 있는데, 이것이 검사 결과를 DB에 저장해서 시각적으로 볼 수 있게 만들라는 것인지, 아니면 다른 의미인지 궁금합니다. 그리고 리포트 안에 어떤 정보가 담겨있어야 하나요?

- [ ] 재고 정합성 오차를 0으로 만드는 게 핵심 목표인데, 이걸 보장하는 데 있어 가장 중요하게 봐야 할 지점이 어디라고 생각하시나요? (Lua 원자성, DB Unique 제약, 이벤트 유실 방지 등)

### 3. 아키텍처와 기술 선택

- [ ] Redis Stream을 Outbox로만 쓰고 Kafka 없이 Consumer가 직접 소비하는 구조와, 지금처럼 Kafka로 한 번 더 relay하는 구조 중 어느 쪽이 동시성 제어와 정합성에 더 효율적인가요? Relay Worker가 죽거나 지연되는 상황이 새로운 장애 포인트를 만들지는 않을까 걱정됩니다.

### 4. 부하 테스트와 측정

- [ ] 병목을 드러내려고 커넥션 풀을 10으로 고정해 측정했습니다. pool 50으로도 재보니 **커넥션 풀 대기 수가 정확히 `톰캣 스레드 200 - pool 크기`로 나와서**, pool을 늘리면 대기하는 스레드 수만 줄고 대기 자체는 사라지지 않는다는 걸 확인했습니다. 실무에서 커넥션 풀 크기는 무슨 기준으로 정하시나요 - DB 코어 수, `max_connections`, 아니면 측정해서 맞추시는지 궁금합니다. 

- [ ] **부하 테스트 중 서버 지표 수집을 어떻게 분리하시나요?** 저희는 앱의 지표 엔드포인트를 200ms마다 폴링했는데, 그 폴링이 부하 요청과 톰캣 스레드를 경쟁해서 응답이 밀렸고 **커넥션 풀 대기 피크를 놓쳐 "풀은 병목이 아니다"라는 반대 결론**을 한동안 들고 있었습니다. 지표 수집용 포트를 따로 열고 나서야 값이 안정됐습니다. 실무에서는 별도 커넥터, 사이드카, 푸시 방식 중 어떤 걸 쓰시나요? 

### 5. 구현 기준

- [ ] 과제 요구사항에 "로그에서 개인정보 마스킹"이 있는데, MySQL은 UNIQUE 제약 위반 시 `Duplicate entry 'tester@test.com' for key ...` 처럼 위반된 값을 에러 메시지에 그대로 넣습니다. 스택트레이스를 통째로 남기면 개인정보가 로그에 들어가고, 안 남기면 500 원인을 추적할 수 없습니다. 저희는 예외 메시지를 제외하고 스택 프레임만 기록한 뒤 `incidentId`로 응답과 로그를 잇는 방식으로 처리했는데, 실무에서는 원인 추적과 마스킹의 상충을 어떻게 푸시는지 궁금합니다.
