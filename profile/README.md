## 🏗️ 아키텍처

### 요청 한 건이 지나가는 길

```text
캠페인 오픈 (매일 정오 12:00:00 / 회차당 10,000장)
    ↓
선착순 발급 요청 (정오 1초에 집중)
    ↓
Redis Lua 원자 판정 (재고 선점 / 중복 차단 / XADD)
    ↓
발급 이력 영속화 (SYNC 즉시 저장 / RELAY 비동기 저장 - 설정으로 전환)
    ↓
발급 확정(CONFIRM) : 저장된 건만 확정 카운터에 반영
    ↓
쿠폰 생애주기 관리 (발급 → 사용 / 취소 / 만료)
    ↓
정합성 검증 배치 (300만 건 전수 검증)
```

### 쿠폰 발급 1차 / 2차 MVP

```text
[1차 - 베이스라인]  현재 기본값 (coupon.issue.persistence.mode=SYNC)
Nginx → API×2 → Redis Lua(원자 판정) → MySQL 동기 저장 → 202


[2차 - 개선]  구현 완료 (mode=RELAY 로 전환)
Client
  ↓
Nginx
  ↓
쿠폰 발급 API
  ↓
Redis (원자적 판정 + XADD)   ← 원자성. 이 계층은 Kafka 를 넣어도 그대로 남는다
  ↓                           202 즉시 응답
Redis Stream (Outbox)
  ↓
Relay 워커 (XREADGROUP → 저장 → CONFIRM → XACK)
  ↓
MySQL
```

> **Kafka 는 도입하지 않기로 확정했습니다.** 넣으려던 이유(팬아웃 / 유실 방지 / 재처리)가
> 전부 Redis Stream 컨슈머 그룹으로 충족되는 것을 측정으로 확인했습니다.

본 시스템은 **대규모 트래픽 환경에서 선착순 쿠폰 발급 시 발생하는 동시성 문제와 데이터 정합성을 안정적으로 처리하는 것**을 목표로 합니다.

사용자의 쿠폰 발급 요청은 **Nginx**를 통해 전달되며, **Redis에서 재고 차감과 중복 발급 여부를 원자적으로 검증**합니다.

발급에 성공한 요청을 **어떻게 영속화할 것인가**가 남은 설계 지점이었고, 이를 비교 측정으로 결정했습니다. MySQL 동기 저장은 동시 20,000 요청에서 **커넥션 풀 대기가 톰캣 스레드 200개 중 190개까지 차오르며** 응답 p99가 4.5초까지 늘어났습니다. 저장을 요청 경로에서 떼어내면 그 대기가 **0**이 되고 p99가 4배 이상 줄어듭니다. 커넥션 풀을 5배 늘려보는 것으로는 해결되지 않았습니다. 그래서 **비동기 저장 + 내구 로그(Outbox)** 구조로 확정했습니다.

내구 로그는 **Redis Stream** 으로 확정했습니다. 판정 Lua 안에서 `XADD` 가 함께 실행되므로 "재고는 줄었는데 이벤트가 없는" 창이 생기지 않고, Kafka 를 도입하더라도 이 계층은 그대로 Redis 로 남습니다.

또한 **Prometheus + Grafana**로 TPS, 응답 시간, Redis Stream 적체 상태를 모니터링하고, 별도의 정합성 검증 Runner를 통해 Redis와 MySQL의 데이터가 일치하는지 검증합니다. 적체는 발급 현황 API의 `pendingQuantity`(판정 완료 수 - 확정 완료 수)로 초 단위 관측이 가능합니다.

## 🔍 정합성 검증

정합성 검증은 발급 파이프라인(Redis → Stream/Kafka → MySQL)의 각 단계에서 데이터가
서로 어긋나지 않는지를 사후적으로 확인하는 모듈입니다. 1차 MVP에서는 **탐지** 까지
구현했고, 2차 MVP에서는 **복구** 와 **실행 스케줄링** 을 추가할 예정입니다.

검증 항목은 트리거 방식과 검증 범위(Scope)를 기준으로 두 그룹으로 나눕니다.

| 그룹 | 트리거 | Scope | 목적 |
|---|---|---|---|
| **A그룹** | 이벤트 마감 시점 | EVENT (단일 회차) | 재고·발급 수량이 회차 단위로 정확히 맞는지 |
| **B그룹** | 주기 배치 | AS_OF_RANGE / ALL | 행 단위 구조, 상태 전이, 시간 정합성이 전체 데이터에서 깨진 곳이 없는지 |

### 동작하는 것 (정합성 검증)

| | 상태 |
|---|---|
| 검증 프레임워크 공통 로직 (`ConsistencyVerificationRunner`, `ConsistencyCheck`, `Scope`, `TriggerType`) | ✅ 동작 |
| **A그룹 체크** | ✅ 2종 구현 완료 |
| **B그룹 체크** | ✅ 6종 구현 완료 |
| 검증 결과 저장 (`VerificationResultJpaRepository`) | ✅ 동작 |
| Spring Batch 대용량 검증 | ✅ 동작 |
| Batch restart 시 상태 직렬화 (Check 타입/Scope/TriggerType → `ExecutionContext`) | ✅ 구현 (`restartRunAsync`) |
| 재현성/멱등성 (동일 데이터셋 반복 실행 시 동일 결과) | ✅ 확인됨 |
| 복구 정책 / 실행 스케줄링 | ❌ 미구현 (2차 MVP 예정) |

### A그룹 : 재고/발급 정합성 (이벤트 마감 시 실행)

#### 1) StockConsistencyCheck (재고 정합성 검증)

- **목적**: 이벤트의 재고 카운터와 실제 발급 이력 건수가 일치하는지 확인
- **검증 로직**:
    1. `coupon_issue`에서 특정 `event_id`(또는 전체 이벤트)를 가진 레코드 수를 실제 발급 건수로 집계
    2. `coupon_event`와 조인하여 `실제 발급 건수 + remaining_stock` 을 `total_stock` 과 비교
    3. `issued_quantity` 컬럼 값과 실제 발급 건수를 비교
- **위반 기준**: 위 두 비교 중 하나라도 불일치하면 위반 건수로 집계
- **검증 대상**: 특정 이벤트 단위 또는 전체 이벤트 단위로 실행 가능

#### 2) RedisMysqlLossConsistencyCheck (Redis-MySQL 유실 검증)

- **목적**: Redis에서 확정된 재고 소진량과 MySQL에 최종 반영된 이력 건수가 일치하는지 확인 (파이프라인 유실 탐지)
- **검증 로직**: `coupon_event.total_stock`과 Redis의 `remainingStock`을 이용해 산출한 "Redis 기준 발급 확정 건수"를, `coupon_history`에 저장된 발급 이력 건수와 비교
- **위반 기준**: 두 값이 불일치하면 위반 건수로 집계 (Redis 확정 → Stream/Kafka → MySQL 반영 구간 중 어딘가에서 유실 또는 중복이 발생했음을 의미)

### B그룹 : 구조/상태 정합성 (주기 배치)

#### 3) IssueHistoryTimeSyncConsistencyCheck (시간 동기화 검증)

- **목적**: `coupon_issue`의 상태값과 시각 필드가 서로 맞는지 확인
- **검증 로직**: 상태별로 대응하는 시각 필드가 채워져 있고 상태와 모순되지 않는지 확인
    - `ISSUED` → `issued_at` 존재
    - `USED` → `used_at` 존재
    - `EXPIRED` → `valid_to` 기준 만료 시점 정합
- **위반 기준**: 상태와 시각 필드가 논리적으로 맞지 않는 경우 위반 건수로 집계

#### 4) StateMachineConsistencyCheck (이력 연속성 검증)

- **목적**: `coupon_history`의 상태 전이가 허용된 상태 머신 흐름을 따르는지 확인
- **검증 로직**: 연속된 `coupon_history` 레코드 간 `from_status → to_status`가 허용 전이 목록에 속하는지 확인
    - 허용 전이: `NULL → ISSUED`, `ISSUED → USED`, `USED → ISSUED`, `ISSUED → EXPIRED`
- **위반 기준**: 허용되지 않은 전이(역방향 전이, 정의되지 않은 상태로의 전이 등)가 존재하면 위반 건수로 집계

#### 5) CouponIssueStructuralConsistencyCheck (발급 이력 행 구조 검증)

- **목적**: `coupon_issue` 한 행 자체의 구조적 결함 탐지
- **발견하려는 문제**:
    - 발급 저장 과정에서 필수값 누락
    - Redis/Stream에서 전달된 식별자(request_id, message_id 등)가 잘못 저장된 경우
    - 사용·만료 상태와 시각 필드 불일치
    - 유효기간(`valid_from`~`valid_to`) 계산 오류

#### 6) CouponHistoryStructuralConsistencyCheck (히스토리 행 구조 검증)

- **목적**: `coupon_history` 한 행의 필수값·시각·전이 형식 검증
- **발견하려는 문제**:
    - 존재하는 상태 이력 행의 필수값, 시각, 전이 형식을 검증
    - `occurred_at`(발생 시각)보다 `recorded_at`(기록 시각)이 앞서는 경우
    - 정의되지 않았거나 제거된 상태/전이가 저장된 경우

#### 7) CouponIssueHistoryStateConsistencyCheck (현재 상태-이력 정합성 검증)

- **목적**: `coupon_issue`의 현재 상태와 `coupon_history`의 최신 이력이 서로 일치하는지 확인
- **발견하려는 문제**:
    - 상태만 변경되고 이력이 저장되지 않은 경우
    - 이력만 저장되고 현재 상태 갱신이 실패한 경우
    - 상태 갱신과 이력 저장이 서로 다른 트랜잭션으로 처리되어 일부만 반영된 경우

#### 8) CouponExpirationLagConsistencyCheck (만료 지연 검증)

- **목적**: 만료 처리 지연 및 만료 이후 사용 처리 여부 검증
- **발견하려는 문제**:
    - 만료 Scheduler 미실행 또는 지연
    - 사용 처리 로직에서 만료 여부를 원자적으로 확인하지 못한 경우
    - 만료된 쿠폰이 실제로 사용 처리된 경우

## 🔧 기술 선택 이유

| 기술 | 선택 이유 |
|---|---|
| **Redis** | 대규모 동시 요청에서 DB에 직접 접근하지 않고 재고 차감과 중복 발급 검증을 빠르게 처리하기 위해 사용. MySQL 비관적 락과 비교 측정한 결과 **락 방식은 동시 20,000에서 절반 이상이 응답을 받지 못했고 Redis 방식은 0%** |
| **Redis Stream** | 발급 처리와 DB 저장을 분리하는 내구 로그(Outbox). 판정 Lua 안에서 `XADD` 가 함께 실행돼 **"재고는 줄었는데 이벤트가 없는" 창이 없음**. 프로세스 강제 종료 시 인메모리 큐는 전량 유실, Stream 은 유실 0 (AOF 켠 상태) |
| **Kafka** ❌ | **도입하지 않기로 확정.** 넣으려던 이유 3가지가 전부 Stream 으로 충족됨 : 팬아웃은 컨슈머 그룹으로 되고(그룹 간 트림 안전성 테스트 통과), 유실 0은 AOF 로 확보되며, 재처리는 PEL + `issue_failure_log` 로 처리 |
| **MySQL** | 쿠폰 발급 이력과 사용자 데이터를 영구적으로 저장하고, Unique 제약 등을 통해 최종적인 데이터 정합성을 보장 |
| **Nginx** | 대량의 요청을 안정적으로 받아 백엔드로 전달하고 트래픽을 분산. 앱 인스턴스를 2대로 나누면 **응답 p99가 45% 개선**되는 것을 확인 (단, 커넥션만 늘리는 것은 오히려 악화) |
| **k6** | 동시 20,000 재현에 JMeter는 부적합. JMeter 스레드는 **OS 스레드(스택 1MB)라 20,000개면 스택만 20GB**가 필요. k6는 goroutine 기반이라 4 vCPU 한 대로 20,000 VU를 생성 |
| **Prometheus + Grafana** | TPS, 응답 시간, Redis Stream 적체 상태 등을 모니터링하여 병목 구간과 시스템 상태를 확인 |
| **Docker Compose** | Redis, MySQL, 모니터링 환경 등을 동일한 환경에서 구성하고 쉽게 재현하기 위해 사용 |

## 📈 부하 테스트 결과

처음부터 모든 기술을 적용하지 않고, **한 단계씩 구현하고 재면서 다음 단계의 근거를 만드는** 방식으로 진행했습니다.
전체 측정 기록과 재현 스크립트는 별도 저장소에 있습니다 → **[Ace_LT 부하 테스트 결과](https://github.com/URECA-Ace/Ace_LT)**

### 무엇을 재려고 했나

| 비교 축 | 답하려는 질문 |
|---|---|
| MySQL 비관적 락 ↔ **Redis Lua 판정** | Redis를 왜 도입하는가 |
| 동기 저장 ↔ **비동기 저장** | 저장을 왜 분리하는가 |
| 인메모리 큐 ↔ **내구 로그(Outbox)** | 비동기면 충분한데, 왜 메시지 큐인가 |
| Stream 팬아웃 ↔ **Kafka 팬아웃** | 팬아웃을 RAM에서 하나, 디스크에서 하나 |

재고와 인스턴스 사양, 커넥션 풀 크기를 **고정한 채 동시 요청 수만 늘려가며** 각 방식이 어디까지 버티고 어떻게 무너지는지를 확인했습니다. 로컬(단일 머신)과 AWS(인스턴스 4대 분리) 두 환경에서 각각 측정했습니다.

### 결과

재고 10,000 / 동시 20,000 기준 응답 p99입니다.

| MySQL 락 | + Redis 판정 | + 비동기 저장 | + 내구 로그 |
|---|---|---|---|
| 14,203ms (에러율 50%) | 4,506ms | **1,101ms** | **846ms** |

본 시스템(300만 건 적재 상태)에서 1차 구조와 2차 구조를 비교한 결과입니다.

| | 1차 (동기 저장) | 2차 (Stream 비동기) | |
|---|---:|---:|---|
| **응답 p99** | 3,640ms | **1,382ms** | **2.6배 개선** |
| **처리량** | 3,386 TPS | **4,457 TPS** | 1.3배 |
| **DB 연결 대기 스레드** | 135 | **0** | 병목 소멸 |
| **초과 발급** | 0건 | 0건 | 양쪽 다 정확 |

### 결론

1. **판정은 Redis 가 필수** : MySQL 락은 동시 20,000에서 에러율 50~84%, 거절(409) 응답조차 돌아오지 않음. Redis 는 0%
2. **저장은 요청 밖으로** : 커넥션 풀 대기 190 → 0. **풀을 5배 늘려도 비동기의 3배 뒤**
3. **큐는 내구 로그로** : 프로세스 강제 종료 시 인메모리 큐는 전량 유실, Stream 은 유실 0 (AOF 켠 상태에서만 성립)

**전 구간에서 초과 발급 0건**이며, 1인 1매도 별도 검증(1,000 요청 / 100 유저 → 발급 100건)했습니다.

    - 서버지표 수집 방법(별도 커넥터? 사이드카나 피시방식?) -> 부하테스트시 폴링해서 보려는 수치가 k6로 응답시간만 확인, 서버에는 어떤일 실제저장,스레드,큐,힙사용량 보려고 테스트 -> A. 로컬에선 모니터링 툴로 메모리 시피유확인, 진행율, TPS, 에러율등 확인, 만약 힙메모리등 서버 직접 폴링없이 떠있는 프로세스 감지 방법찾아보기 / 배포한 상태에서는 회사 모니터링툴이라 설명 어렵(폴링수집 대신 특정 도구: 비쥬얼 VM사용했었다.), K6는 TPS-시계열,그라파다연결해서 시각화
